# Rust release workflow (maintainer guide)

This document explains how the `rust-release.yml` workflow publishes new Rust XCFramework artifacts, how `rust/Pin.json` binds the Swift package to a specific artifact, and how the drift guard keeps the two in sync. It is scoped to the Rust binary; the Swift package release process is separate.

## How the pieces fit together

- **`rust-release.yml`**: publishes a new Rust XCFramework as a GitHub release with four assets – the zip, its checksum, a machine-readable manifest, and release notes. The workflow is `workflow_dispatch`-only.
- **`rust/Pin.json`**: a verbatim copy of the release manifest for the currently pinned version. `Package.swift` mirrors its `xcframework_url` and `checksum` values as literals because manifest-evaluation file I/O is unreliable for URL-based dependency consumers.
- **CI drift guard** (`scripts/rust/release/check-pin.sh`): on every PR, recomputes the source hash and compares it against `Pin.json.source_hash_sha256`. On mismatch, CI fails with a message pointing at `cut-release.sh`.
- **Pre-release pin guard** (`scripts/rust/release/check-prerelease-pin.sh`): on PRs targeting `main`, fails if `Pin.json.version` contains a `-` suffix, unless the repository variable `ALLOW_PRERELEASE_PIN=1` is set.
- **Wrapper drift check** (`scripts/rust/check-wrapper-drift.sh`): runs in `ci.yml` (paths-gated) and `rust-release.yml` (always-on, before `swift test`). It rebuilds the static library, regenerates the Swift wrapper into a temp dir, and `git diff --no-index`'s the result against the committed `Sources/TokenizersFFI/Generated/TokenizersFFI.swift`. A nonzero diff fails CI with a message pointing at `regenerate-wrapper.sh`.
- **`scripts/rust/release/cut-release.sh`**: the single maintainer command that drives the whole flow.

## UniFFI bindgen and the committed Swift wrapper

The Rust↔Swift FFI is generated by [UniFFI](https://mozilla.github.io/uniffi-rs/). The full release build (`scripts/rust/build/build-rust-xcframework.sh`) and the standalone helper (`scripts/rust/build/build-uniffi-bindings.sh`) both invoke a workspace-pinned `uniffi-bindgen-swift` binary against the freshly built host static library and emit three artifacts into `rust/target/uniffi-bindings/`:

- `TokenizersRust.h` – C header that the XCFramework exposes.
- `module.modulemap` – modulemap that names the C module `TokenizersRust`.
- `TokenizersFFI.swift` – the high-level Swift wrapper.

The header and modulemap go straight into the XCFramework (they are part of the binary release). The Swift wrapper is **committed** at `Sources/TokenizersFFI/Generated/TokenizersFFI.swift` and consumed by the `TokenizersFFI` SwiftPM target (a non-product target that the public `Tokenizers` target depends on).

The committed wrapper is the source of truth for what the binary release exposes. To keep the two in sync:

- **Neither build script writes to `Sources/TokenizersFFI/Generated/`.** Both `build-rust-xcframework.sh` and `build-uniffi-bindings.sh` only write to `rust/target/uniffi-bindings/`. CI and the release workflow only ever read the committed wrapper; they never overwrite it.
- **`scripts/rust/regenerate-wrapper.sh`** is the developer-facing command that rebuilds the bindgen artifacts (via `build-uniffi-bindings.sh`) and copies the freshly generated wrapper over the committed one. Run it after touching `rust/src/`, `rust/uniffi.toml`, or the bindgen binary version.
- **`scripts/rust/check-wrapper-drift.sh`** runs in CI and the release workflow and fails if the committed wrapper drifts from what the bindgen would emit. It calls `build-uniffi-bindings.sh` rather than the full XCFramework build, so the per-target `cargo build` matrix and `xcodebuild -create-xcframework` are skipped — the drift job only pays for the host static library plus the bindgen binary. Without this guard, a stale committed wrapper could ship inside a release whose `source_hash_sha256` describes the freshly regenerated wrapper rather than the one in the git commit at `GITHUB_SHA`.

The wrapper goes through one post-bindgen step: `regenerate-wrapper.sh` and `check-wrapper-drift.sh` prepend a `// swift-format-ignore-file` marker so the project's swift-format lint skips the generated file. `.swift-format-ignore` files would be a cleaner mechanism, but the support landed too recently to be in the swift-format that ships with the stable Swift toolchain we target. **TODO:** drop the prepend in both scripts and use a `.swift-format-ignore` file at the repo root once a swift-format release including [apple/swift-format#1197](https://github.com/apple/swift-format/pull/1197) ships in our stable Swift toolchain.

UniFFI 0.31.x's Swift bindgen used to emit `String(bytes:encoding:.utf8)!` for `FfiConverterString`, which routes through Foundation's NSString decoder and silently strips a leading U+FEFF BOM during UTF-8 decoding — corrupting BOM-prefixed vocabulary entries (e.g. the Gemma tokenizer's id 122661). The fix lives on a fork pinned via `[patch.crates-io]` in `rust/Cargo.toml`. **TODO:** drop that block and bump the `uniffi` version in `[dependencies]` once [mozilla/uniffi-rs#2889](https://github.com/mozilla/uniffi-rs/pull/2889) is included in a uniffi-rs release.

## Overview of `rust-release.yml`

The workflow is split into two jobs:

- **`build-validate`**: verifies the dispatched commit matches `expected_commit`, builds the XCFramework, runs `swift test` against the freshly built artifact, computes the canonical source hash, writes the release manifest JSON, and uploads all four files (archive, checksum, manifest, release notes) as workflow artifacts. Runs under `contents: read`.
- **`publish`**: downloads the workflow artifacts and creates the GitHub release via `gh release create --target "$GITHUB_SHA" ...`. Runs under `contents: write` and is gated by a GitHub Environment (`rust-release`) with the maintainer as a required reviewer.

The split puts the approval prompt exactly at the write boundary. A failed build or a mismatched `expected_commit` fails the workflow before the publish job is ever queued for approval.

## One-time setup

### GitHub Environment

Create a repository Environment named `rust-release` under **Settings → Environments → New environment**:

1. Add the maintainer as a required reviewer.
2. Confirm "Prevent self-review" is **disabled** (the maintainer is their own reviewer).
3. Save.

The `publish` job references `environment: rust-release`. Without this configuration the publish job fails when it tries to enter the environment.

## Cutting a release

Run `scripts/rust/release/cut-release.sh <version>` from the branch you want to publish – typically a Rust-touching PR branch. The script:

1. Validates the working tree is clean and the branch is pushed to origin.
2. Records local `HEAD` as the expected commit.
3. Dispatches `rust-release.yml` against the current branch with `version` and `expected_commit=<local HEAD>`.
4. Waits for the run to finish.
5. Verifies `gh run view --json headSha` equals the expected commit.
6. Downloads the release manifest asset.
7. Cross-checks that the manifest's `version`, `git_commit`, and `source_hash_sha256` match what the script expects.
8. Writes the manifest verbatim to `rust/Pin.json` and commits the bump on the current branch with a standard message.

Push the branch afterwards to trigger CI with the refreshed pin.

## Drift guard

Every PR runs `scripts/rust/release/check-pin.sh`, which:

1. Reads `rust/Pin.json` and validates its `hash_schema_version`.
2. Recomputes the canonical source hash via `scripts/rust/hash-source.sh`.
3. Fails if the hashes differ, with a message that tells the maintainer to cut a new Rust release on the branch.

The guard makes it structurally impossible to merge a PR where the Rust source and the pinned XCFramework disagree.

Because `hash_schema_version` is part of the comparison, a change to the hash input set or the hashing strategy must bump the schema version in both `scripts/rust/release/check-pin.sh` and anywhere else that asserts it. Existing pins stop passing the guard until a fresh release is cut under the new scheme.

## Pre-release pin guard

`scripts/rust/release/check-prerelease-pin.sh` runs as a CI step on PRs targeting `main`. It fails when `rust/Pin.json.version` contains a `-` suffix (e.g., `0.3.3-rc.1`), which keeps pre-release pins off `main` by default.

To merge a pre-release pin intentionally – for example, to validate the release flow on a release-prep branch – set the repository variable `ALLOW_PRERELEASE_PIN=1` under **Settings → Secrets and variables → Actions → Variables**. Unset it once the stable pin is in place.

## Trust boundary

`rust-release.yml` has `contents: write` (on the `publish` job) and runs the workflow file from whatever ref is dispatched. A branch that modifies the workflow could publish bogus assets if a maintainer dispatches the release against it.

- Do not dispatch `rust-release.yml` against an external contributor's PR branch directly. Merge or cherry-pick the reviewed Rust source changes onto a maintainer-owned branch (or `main`) first, then run `cut-release.sh` there.
- Treat the release workflow and `cut-release.sh` as maintainer-only tools. External contributors cannot trigger `workflow_dispatch` – only repository write access can – but this discipline protects against social-engineering dispatches.

## Bumping the hash schema

The `hash_schema_version` field exists so the hash input set can evolve without silently accepting stale pins. To bump it:

1. Change `scripts/rust/hash-source.sh` (or whichever input set is changing).
2. Bump `SUPPORTED_HASH_SCHEMA_VERSION` in `scripts/rust/release/check-pin.sh` and any other tooling that asserts the schema version.
3. Merge the schema change.
4. Cut a new Rust release on the new schema. Until that release is cut, the drift guard fails because the existing pin's schema version is stale.
