# Rust release workflow (maintainer guide)

This document explains how the `rust-release.yml` workflow publishes new Rust artifactbundle releases, how `rust/Pin.json` binds the Swift package to a specific artifact, and how the drift guard keeps the two in sync. It is scoped to the Rust binary; the Swift package release process is separate.

## How the pieces fit together

- **`rust-release.yml`**: publishes a new Rust artifactbundle (SE-0482 `staticLibrary` artifact bundling Apple and Linux slices in one zip) as a GitHub release with three assets – the zip, its checksum, and a machine-readable manifest – plus an auto-generated release-notes body. The workflow is `workflow_dispatch`-only.
- **`rust/Pin.json`**: a verbatim copy of the release manifest for the currently pinned version. `Package.swift` mirrors its `artifactbundle_url` and `checksum` values as literals because manifest-evaluation file I/O is unreliable for URL-based dependency consumers.
- **CI drift guard** (`scripts/rust/release/check-pin.sh`): on every PR, recomputes the source hash and compares it against `Pin.json.source_hash_sha256`. On mismatch, CI fails with a message pointing at `cut-release.sh`.
- **Pre-release pin guard** (`scripts/rust/release/check-prerelease-pin.sh`): on PRs targeting `main`, fails if `Pin.json.version` contains a `-` suffix, unless the repository variable `ALLOW_PRERELEASE_PIN=1` is set.
- **Wrapper drift check** (`scripts/rust/check-wrapper-drift.sh`): runs in `ci.yml` (paths-gated) and `rust-release.yml`'s `apple-build` job (always-on, between the per-target `cargo build` matrix and bundle assembly). It rebuilds the host static library, regenerates the Swift wrapper into a temp dir, and `git diff --no-index`'s the result against the committed `Sources/TokenizersFFI/Generated/TokenizersFFI.swift`. A nonzero diff fails CI with a message pointing at `regenerate-wrapper.sh`.
- **`scripts/rust/release/cut-release.sh`**: the single maintainer command that drives the whole flow.

## UniFFI bindgen and the committed Swift wrapper

The Rust↔Swift FFI is generated by [UniFFI](https://mozilla.github.io/uniffi-rs/). The standalone helper `scripts/rust/build/build-uniffi-bindings.sh` invokes a workspace-pinned `uniffi-bindgen-swift` binary against the freshly built host static library and emits three artifacts into `rust/target/uniffi-bindings/`:

- `TokenizersRust.h` – C header that the artifactbundle exposes.
- `module.modulemap` – modulemap that names the C module `TokenizersRust`. The per-platform build scripts post-process this with `scripts/rust/build/strip-modulemap-uses.sh` to drop the bindgen-emitted `use "Darwin"` / `use "_Builtin_*"` directives, since those reference clang modules that exist only on Apple and break the module load on Linux.
- `TokenizersFFI.swift` – the high-level Swift wrapper.

The per-platform build scripts (`scripts/rust/build/build-rust-apple-slices.sh` for Apple, `scripts/rust/build/build-rust-linux-archives.sh` for Linux) shell out to the helper as part of producing their slices, then copy the (use-stripped) header and modulemap into their staging dir's `include/`. The artifactbundle assembler picks whichever staging dir's `include/` is present (preferring the Apple one when both are — the contents are identical post-strip) and stages it once at the bundle's top level. Every variant in `info.json` references that single `include/` via `staticLibraryMetadata.headerPaths` / `moduleMapPath`, since the C ABI is platform-neutral.

The Swift wrapper is **committed** at `Sources/TokenizersFFI/Generated/TokenizersFFI.swift` and consumed by the `TokenizersFFI` SwiftPM target (a non-product target that the public `Tokenizers` target depends on).

The committed wrapper is the source of truth for what the binary release exposes. To keep the two in sync:

- **None of the build scripts write to `Sources/TokenizersFFI/Generated/`.** `build-uniffi-bindings.sh` writes to `rust/target/uniffi-bindings/`; the per-platform build scripts additionally write to their staging dirs (`rust/target/apple-build/` and `rust/target/linux-build/`). CI and the release workflow only ever read the committed wrapper; they never overwrite it.
- **`scripts/rust/regenerate-wrapper.sh`** is the developer-facing command that rebuilds the bindgen artifacts (via `build-uniffi-bindings.sh`) and copies the freshly generated wrapper over the committed one. Run it after touching `rust/src/`, `rust/uniffi.toml`, or the bindgen binary version.
- **`scripts/rust/check-wrapper-drift.sh`** runs in CI and the release workflow and fails if the committed wrapper drifts from what the bindgen would emit. It calls `build-uniffi-bindings.sh` rather than a full per-platform build, so the per-target `cargo build` matrix and the artifactbundle assembly are skipped — the drift job only pays for the host static library plus the bindgen binary. The check also covers the staged `include/TokenizersRust.h` and `include/module.modulemap` (post-strip) when an `apple-build/` or `linux-build/` staging directory is present, so a release run guarantees the headers shipped in the bundle match the source at `GITHUB_SHA`.

The wrapper goes through one post-bindgen step: `regenerate-wrapper.sh` and `check-wrapper-drift.sh` prepend a `// swift-format-ignore-file` marker so the project's swift-format lint skips the generated file. `.swift-format-ignore` files would be a cleaner mechanism, but the support landed too recently to be in the swift-format that ships with the stable Swift toolchain we target. **TODO:** drop the prepend in both scripts and use a `.swift-format-ignore` file at the repo root once a swift-format release including [apple/swift-format#1197](https://github.com/apple/swift-format/pull/1197) ships in our stable Swift toolchain.

The `[patch.crates-io]` block in `rust/Cargo.toml` pins a uniffi-rs fork that adds two Swift bindgen visibility options, `implementation_only_ffi_module_import` and `internal_ffi_converter_helpers`. `rust/uniffi.toml` sets both, which keeps the lower-level Rust FFI module and its converter helpers out of the generated wrapper's public Swift interface. The pinned revision must stay identical to swift-hf-api's: both packages patch the same crates, and a mismatch means the two artifactbundles are built against different bindgen behavior. **TODO:** drop the block and use the plain `uniffi` dependency once these options ship in a uniffi-rs release.

## Overview of `rust-release.yml`

The workflow is split into four jobs to keep the cross-platform builds independent and the write boundary tight:

- **`apple-build`** (macos-latest, `contents: read`): verifies the dispatched commit matches `expected_commit`, runs `build-rust-apple-slices.sh` to cross-compile the five Apple targets and stage them under `rust/target/apple-build/` (with `apple-macos/` and `apple-ios-simulator/` lipoed into universal slices), runs the wrapper-drift check, and uploads the staging dir as the `apple-build` workflow artifact.
- **`linux-build`** (ubuntu-22.04, `contents: read`): verifies the dispatched commit, installs the aarch64 cross-toolchain plus a Cargo `linker` mapping for `aarch64-unknown-linux-gnu` (so the x86_64 host can produce both Linux slices), runs `build-rust-linux-archives.sh`, and uploads `rust/target/linux-build/` as the `linux-build` workflow artifact.
- **`assemble`** (macos-latest, `contents: read`): downloads both build artifacts, runs `assemble-artifactbundle.sh` to produce the unified `TokenizersRust.artifactbundle.zip` plus a SwiftPM-style checksum, asserts that all five variants ended up in `info.json` (a partial bundle would resolve silently on the host triple but break consumers building for unsupported triples), runs `swift build` against the staged bundle as a smoke test, computes the source hash, writes the release manifest, generates release notes via `scripts/rust/release/rust-release-notes.py`, and uploads the publishable artifacts.
- **`publish`** (macos-latest, `contents: write`, environment `rust-release`): downloads the assembled artifacts and creates the GitHub release via `gh release create --target "$GITHUB_SHA" ...`. Gated by a GitHub Environment with the maintainer as a required reviewer.

The split puts the approval prompt exactly at the write boundary. A failed build, a mismatched `expected_commit`, a missing variant, or a smoke-test failure stops the workflow before the publish job is ever queued for approval. The `Verify expected commit` step lives in `.github/actions/verify-expected-commit/action.yml` so the apple-build and linux-build jobs share one source.

## One-time setup

### GitHub Environment

Create a repository Environment named `rust-release` under **Settings → Environments → New environment**:

1. Add the maintainer as a required reviewer.
2. Confirm "Prevent self-review" is **disabled** (the maintainer is their own reviewer).
3. Save.

The `publish` job references `environment: rust-release`. Without this configuration the publish job fails when it tries to enter the environment.

## Cutting a release

Run `scripts/rust/release/cut-release.sh <version>` from the branch you want to publish – typically a Rust-touching PR branch. The script:

1. Validates the working tree is clean and the branch is pushed to origin.
2. Records local `HEAD` as the expected commit.
3. Dispatches `rust-release.yml` against the current branch with `version` and `expected_commit=<local HEAD>`.
4. Waits for the run to finish.
5. Verifies `gh run view --json headSha` equals the expected commit.
6. Downloads the release manifest asset.
7. Cross-checks that the manifest's `version`, `git_commit`, and `source_hash_sha256` match what the script expects.
8. Writes the manifest verbatim to `rust/Pin.json`, rewrites `Package.swift`'s inline `tokenizersRustArtifactBundleURL` / `tokenizersRustArtifactBundleChecksum` constants from the manifest's `artifactbundle_url` / `checksum` fields, and commits both files on the current branch with a standard message.

Push the branch afterwards to trigger CI with the refreshed pin.

## Drift guard

Every PR runs `scripts/rust/release/check-pin.sh`, which:

1. Reads `rust/Pin.json` and validates its `hash_schema_version`.
2. Recomputes the canonical source hash via `scripts/rust/hash-source.sh`.
3. Fails if the hashes differ, with a message that tells the maintainer to cut a new Rust release on the branch.

The guard makes it structurally impossible to merge a PR where the Rust source and the pinned artifactbundle disagree.

Because `hash_schema_version` is part of the comparison, a change to the hash input set or the hashing strategy must bump the schema version in both `scripts/rust/release/check-pin.sh` and anywhere else that asserts it. Existing pins stop passing the guard until a fresh release is cut under the new scheme.

## Pre-release pin guard

`scripts/rust/release/check-prerelease-pin.sh` runs as a CI step on PRs targeting `main`. It fails when `rust/Pin.json.version` contains a `-` suffix (e.g., `0.3.3-rc.1`), which keeps pre-release pins off `main` by default.

To merge a pre-release pin intentionally – for example, to validate the release flow on a release-prep branch – set the repository variable `ALLOW_PRERELEASE_PIN=1` under **Settings → Secrets and variables → Actions → Variables**. Unset it once the stable pin is in place.

## Trust boundary

`rust-release.yml` has `contents: write` (on the `publish` job) and runs the workflow file from whatever ref is dispatched. A branch that modifies the workflow could publish bogus assets if a maintainer dispatches the release against it.

- Do not dispatch `rust-release.yml` against an external contributor's PR branch directly. Merge or cherry-pick the reviewed Rust source changes onto a maintainer-owned branch (or `main`) first, then run `cut-release.sh` there.
- Treat the release workflow and `cut-release.sh` as maintainer-only tools. External contributors cannot trigger `workflow_dispatch` – only repository write access can – but this discipline protects against social-engineering dispatches.

## Bumping the hash schema

The `hash_schema_version` field exists so the hash input set can evolve without silently accepting stale pins. To bump it:

1. Change `scripts/rust/hash-source.sh` (or whichever input set is changing).
2. Bump `SUPPORTED_HASH_SCHEMA_VERSION` in `scripts/rust/release/check-pin.sh` and any other tooling that asserts the schema version.
3. Merge the schema change.
4. Cut a new Rust release on the new schema. Until that release is cut, the drift guard fails because the existing pin's schema version is stale.
